2 业务决定与交互输入
R01 P1 字符串 false 被当成同意执行
定位 catalog.py 125-146；trade.py 48-62；cli.py 106-110
依据 REQ-007 商品审核；REQ-016 卖家接受或拒绝预约
触发与复现 在 review_product 的 JSON 参数中传入 "approve":"false"；在 seller_decision 中传入 "
accept":"false"。两者都是合法 JSON，但类型不是布尔值。
实际结果 复现中，待审核商品转为 PUBLISHED，待处理预约转为 CONFIRMED。Python 将非空字符串视为真，
程序没有拒绝错误类型。审核中的驳回原因检查也被跳过。
预期行为 approve 和 accept 只接受 JSON 的 true 或 false。字符串、数字、null、数组和对象应返回
INVALID_INPUT，且不改变状态。
根因与影响 代码直接以 if approve 和 if accept 分支，没有先验证 type(value) is bool。CLI 仅验证参
数对象和 token 字段，随后直接调用服务。
影响范围 输入错误会产生相反的审核或交易决定，且以成功结果提交数据库。执行者仍须具备相应权限；这项
问题并不使普通用户取得管理员权限。
修正建议 在业务服务入口统一校验严格布尔类型，再执行权限和状态处理。不能用 bool(value) 转换字符串
，也不能仅在 CLI 层过滤。
复验标准 对 true、false 分别检查正确分支；对 "false"、"true"、0、1、null、[]、{} 检查均被拒绝，且
商品、预约、审核记录和成功日志无新增变更。
R02 P2 合法 JSON 中的错误类型可使交互终端退出
定位 queries.py 65-68；cli.py 115-133
依据 USAGE 中的交互命令约定；CLI run 方法的错误后继续可用约定
触发与复现 登录后输入 list_products {"keyword":1}。
实际结果 keyword.replace 触发 AttributeError，该异常穿透 Shell.run。复现确认交互循环未正常返回，
后续 quit 未被消费。
预期行为 终端返回参数类型错误，并继续接受下一条命令。无效参数不应终止整个会话。
根因与影响 业务入口对 keyword 没有字符串校验。Shell.run 只捕获 MarketError、JSONDecodeError、
TypeError、ValueError 和退出信号，没有处理这条 AttributeError 路径。
影响范围 普通输入错误导致交互中断。异常退出还会跳过循环末尾 logout，当前会话记录将继续留存至过期
或主动注销。
修正建议 为各命令建立明确的参数校验，优先将错误输入转换为 MarketError；用 finally 保证会话退出清
理。对超大页码等边界也应返回可读错误。
复验标准 通过 Shell.run 连续输入错误 keyword、合法查询和 quit，确认合法查询仍执行且最终会话失效。
避免仅补捕获 AttributeError 而掩盖内部代码缺陷。

3 数据库与故障处理
R03 P2 失败审计再次遇到锁冲突时泄漏数据库异常
定位 core.py 97-102 及 160-166；database.py 93-96
依据 REQ-025 失败后保持一致；MarketError 稳定错误输出约定
触发与复现 一个独立连接持续持有 BEGIN IMMEDIATE 写锁，另一个业务写入等待超时。本次为缩短复现，将
探针连接 busy_timeout 临时调至 1 毫秒。
实际结果 业务锁冲突进入 sqlite3.Error 分支后，failure 再次执行 BEGIN IMMEDIATE，同样遇到锁冲突。
最终抛出原生 OperationalError，没有返回预期 MarketError。
预期行为 向调用者返回受控的可重试数据库错误。失败日志无法写入时应保留原业务错误语义，并明确记录或
传递审计失败信息。
根因与影响 write 的 except 分支直接调用 failure；failure 自身的连接、加锁、写入和提交均没有异常隔
离，能够覆盖正在处理的原始错误。
影响范围 数据库忙时交互终端可能异常退出，调用者拿不到约定错误封装。默认设置下两次等待都可消耗 10
秒，异常路径的延迟可能累积。
修正建议 为失败审计建立单独的受控错误边界和有限重试，业务返回保持 DB_ERROR。审计无法持久化时不能
静默伪报已记录，应采用明确的诊断或可靠补记方案。
复验标准 在持续锁占用和随后释放两种场景验证返回类型、等待上限和日志策略。不得仅捕获后忽略异常，从
而声称失败日志已经保存。
R04 P2 非业务异常回滚后没有失败审计
定位 core.py 154-166；trade.py 36-43；tests/test_market.py 354-400
依据 REQ-025 原子性；REQ-026 关键操作与失败日志
触发与复现 通过现有构造器故障注入接口，在 reservation_inserted 检查点抛出 RuntimeError。该接口已
有设计说明，不需要修改生产源码。
实际结果 新预约成功回滚，预约行数为 0；异常仍为 RuntimeError，RESERVE 失败审计数量增加 0。原有故
障测试只注入 MarketError，未覆盖该分支。
预期行为 未预期的运行异常发生时，保持业务回滚，并留下不含敏感信息的失败诊断和可关联操作记录。
根因与影响 内部 except Exception 负责 rollback 后重新抛出；外层只处理 MarketError 与
sqlite3.Error，其余 Exception 不进入 failure。
影响范围 一致性保护在该场景有效，但故障追溯存在空白，且 CLI 对这种异常没有稳定输出。此结论不代表
当前代码已经发生过真实 RuntimeError 故障。
修正建议 增加统一的未预期异常处理策略，保存关联动作、对象及安全错误码；详细异常仅进入受控诊断。是
否向上重新抛出由服务契约明确规定。
复验标准 分别以 MarketError、sqlite3.Error 和 RuntimeError 注入，检查业务、回执、成功日志全部回滚
，并验证失败审计或明确的审计失败处理。

4 查询快照与关联审计
R05 P2 分页总数和列表不在同一读取快照
定位 queries.py 47-83；database.py 93
依据 REQ-011 多条件商品查询；REQ-012 排序和分页
触发与复现 在 list_products 的 count 查询完成后、列表查询前，由独立连接提交商品下架。探针精确安排
两条 SQL 之间的提交，不替换查询结果。
实际结果 本次数据集中返回 total=1、items=[]、page=1。两条查询各自读取当时已提交的数据，因此同一个
响应内部口径不同。
预期行为 一次列表响应中的 total 和 items 来自同一数据库快照。跨次翻页期间数据变化仍需另行定义，不
能与单次响应内部不一致混淆。
根因与影响 连接使用 isolation_level=None；list_products 没有显式 BEGIN，count 和 rows 两条
SELECT 不受同一个读事务约束。固定排序不能解决快照问题。
影响范围 并发发布、下架或预约期间，页面可能显示有结果但当前页为空，影响分页提示与查询可信度。写入
原子性和有效预约唯一性不受此问题直接影响。
修正建议 在较短的显式读事务中完成身份、count 和 rows 查询，结束后及时关闭连接；同时检查其他多次读
取组成一个响应的方法是否需要一致快照。
复验标准 安排发布和下架在两次 SELECT 之间提交，确认响应保持同一快照；另测同价商品稳定排序和跨页更
新语义。
R06 P2 违规关闭交易的审计遗漏关联记录变化
定位 core.py 70-95 及 140-148；trade.py 184-211
依据 REQ-026 前后状态及取消申请和完成标记可关联追溯
触发与复现 对处于 CANCEL_PENDING、同时存在待处理取消申请的商品执行 restrict。
实际结果 预约和取消申请均转为 CLOSED，但 RESTRICT 日志的 before 与 after 仅包含 products；日志详
情中均没有被关闭的预约 ID 与取消申请 ID。
预期行为 这次处置的日志能够关联被关闭的预约、取消申请，并记录其前后状态。管理员有因关闭的记录也应
覆盖实际连带变更。
根因与影响 snapshot 只按 object_id 查同 ID 的单条记录，并只从 reservations 扩展到 products。
restrict 的对象是商品，缺少从商品到有效预约及待处理申请的展开。
影响范围 数据库里的关闭结果正确，但单条处置证据不能说明关闭了哪条交易、哪份申请。后续发生多轮预约
时，审计还原需要额外推断。
修正建议 为聚合状态变更提供显式的审计上下文，在更新前后捕获相关记录的 ID、状态、确认轮次和标记。
控制字段范围，避免复制密码、会话和无关描述。
复验标准 覆盖 restrict、close_disabled_trade、取消拒绝和撤回，逐项核对所有变动对象的 ID 与前后状
态。保留审计不可改删测试。

5 幂等请求与整改顺序
R07 P2 null 请求键绕过交易幂等回执
定位 core.py 111 及 126-139 及 149-153；trade.py 19-46
依据 REQ-014 重复预约与请求幂等；CONTRACTS 的同键重试返回原结果
触发与复现 通过 JSON 显式传入 "key":null，执行 reserve 后以相同参数重试。其他需要 key 的交易方法
也共用这一分支。
实际结果 首次预约成功为 PENDING，新增回执行数为 0；再次提交返回 STALE_VERSION，不能取回首次成功结
果。
预期行为 需要幂等保障的交易命令必须拒绝缺失或非字符串请求键。合法键的同参数重试应返回首次保存的结
果。
根因与影响 交易方法虽然要求传 key 参数，但没有检查其值；Core.write 把 None 作为“不启用回执”的通
用标记，直接跳过校验、查询和保存。
影响范围 不会因此产生第二条有效预约，但响应丢失后的重试失去约定的恢复能力。方法签名要求 key 不等
于请求键已经有效。
修正建议 在所有必须幂等的交易入口执行 required(key, 请求键, 100)，并明确无回执写操作与必须回执写
操作的调用约定。
复验标准 对 null、空串、纯空白、数字和超长键验证事务前拒绝；对有效键测试同参数重放、跨动作误用、
不同参数冲突和完成时间稳定。
